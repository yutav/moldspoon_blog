こんにちは！朝晩がすっかり冷え込んできましたね。[yuku_tas](https://twitter.com/yuku_tas)です。

ハッカーの皆様は、RDSのマスターパスワードを本番で変えたことはありますか？

退職者が知っていた、どこかに貼ってしまった、そもそも誰も覚えていない。**変えなければいけない日は突然やってきます。** でも「変えた瞬間、動いているアプリはどうなるのか」を実際に見たことがある人は、案外少ないのではないでしょうか。

公式ドキュメントには「ダウンタイムは発生しない」と書いてあります。そこで、**使い捨てのRDSを作って実際に変更し、0.5秒〜1秒ごとにログインを試して記録しました。**

## 先に結論

- パスワードを変えても、**既存の接続・実行中のクエリ・開いているトランザクションは無事でした**
- 新旧の入れ替わりは一瞬で、API呼び出しの約3.6秒後でした。「どちらでも入れない時間」は計測間隔の中では見えませんでした
- ただし**新しい接続は、古いパスワードだと即座に失敗します。** ここがアプリの止まる場所です
- <span className="hoso">Secrets Managerの即時ローテーションでは、シークレットから取得した値でのログインが約60秒間失敗しました（6回すべて）</span>
- ログインできない原因が**パスワード間違い・アカウントロック・権限喪失なら再設定で直りました。Host Blockedは直りません**

## 試した環境

- RDS for MySQL **8.4.11** / db.t4g.micro / Single-AZ / gp3 20GB / 東京リージョン
- ほぼ無負荷の、計測後に削除するDB
- `max_connections` 60 / `max_connect_errors` 100 / `skip_name_resolve` OFF
- 計測はCloudShellからboto3とPyMySQLで行いました
- t は変更APIを呼んだ時点からの秒数です

ローテーション以外の項目は**1回ずつの計測**です。インスタンスサイズや負荷が変われば数字は動くはずなので、「このくらいの桁で起きる」という目安として読んでください。

**Multi-AZ、リードレプリカ、PostgreSQL、Aurora、負荷がかかった状態は試していません。**

## 手順

### 自分でパスワードを決める場合

<CodeBlockTitle title="手動で変更する" />

```bash
# 履歴に平文を残さないよう、read で受ける
read -rs NEW_PW

aws rds modify-db-instance --no-cli-pager \
  --db-instance-identifier mydb \
  --master-user-password "$NEW_PW" \
  --query 'DBInstance.[DBInstanceStatus,PendingModifiedValues]'
```

`--apply-immediately` は要りません。AWS CLIのリファレンスどおり、付けなくても変更は非同期ですぐに適用されます。メンテナンスウィンドウまで待ってはくれないので、**実行した時点で本番に効く**と思ってください。

なお、`/`、`@`、`"`、空白はパスワードに使えません。試すと次のエラーで即拒否されました。

```text
Only printable ASCII characters besides '/', '@', '"', ' ' may be used.
```

ここから分かることが2つあります。

**1つ目は、状態が `available` でも完了とは限らないこと**です。呼び出しの直後は `available` のままなので、状態だけを見る確認だと「もう終わった」と誤認します。`PendingModifiedValues` も一緒に見るか、`resetting-master-credentials` になるのを確かめてから待ちましょう。

**2つ目は、状態が戻るのを待たなくても新パスワードは効いていること**です。約60秒の `resetting-master-credentials` は、新パスワードが使えない時間ではありませんでした。

### 既存の接続はどうなったか

変更の前後で次の4つを動かし続けましたが、**いずれも無傷でした。**

- 保持した接続での `SELECT 1`（90回、エラーなし）
- 変更をまたいで実行した `SELECT SLEEP(45)`（完走）
- 変更前に開いたトランザクションの `COMMIT`（成功）
- 別ユーザー `app_user` の新規ログイン（175回すべて成功）

ということは、**接続プールが接続を持ち続けている間は問題が表に出ません。** 新しい接続を張るタイミング、つまりプールの寿命切れ、再起動、デプロイ、スケールアウトのときに初めて失敗します。「変更した直後は平気だったのに、夜のデプロイで落ちた」という形になりやすいはずです（この部分は計測からの推測です）。

## リスク1：打ち間違えると約1分直せない

変更の約1秒後にもう一度変更を呼ぶと、拒否されました。

```text
InvalidDBInstanceState
```

有効なのは1回目のパスワードで、状態が `available` に戻ったのは2回目の呼び出しから約61秒後でした。つまり、<span className="hoso">打ち間違えたパスワードで確定すると、新しい接続が通らないまま約1分は直せません。</span>

変更するパスワードは、シェルに入力する前にシークレットの保管先へ入れておき、そこからコピーして使うのが安全です。

## リスク2：再接続の嵐は、意外と大丈夫だった

パスワードを変えた直後に、古いパスワードのアプリが再接続を繰り返す場面を想定しました。**誤ったパスワードでの20並列のログインを60秒間**続け、その間に毎秒、正しいパスワードでのログインも試しています。

- 失敗は **17,579回**（すべて `1045 Access denied`）
- 正しいパスワードでの新規ログインの失敗は **0回**
- 新規接続の所要時間の中央値は約45ms（平常時は単発で8〜35ms）
- `Threads_connected` のピークは24（`max_connections` は60）
- ブロックは発生せず

毎秒約290回も失敗しているのに `max_connect_errors` の100に届きません。`performance_schema.host_cache` を見ると、`SUM_CONNECT_ERRORS` は0のままで、`COUNT_AUTHENTICATION_ERRORS` だけが増えていました。**認証失敗はブロックの計数に入りません。**

ただし、これはパスワードの間違いでブロックされないという意味であって、次のリスク3とは別の話です。また、今回は無負荷のDBです。負荷がかかったDBで同じことが起きても平気だとは言えません。

## リスク3：Host Blockedはパスワードでは直らない

**ここが今回いちばん知っておきたいところです。** 認証失敗は数えられませんが、**認証の前に切断された接続は数えられます。**

TCPでつないで、認証に進まず切断する。これを正常なログインを挟まずに繰り返すと、**101回目でブロックされました。** 解除後にもう一度試しても101回目でした。

```text
1129: Host '...' is blocked because of many connection errors; unblock with 'mysqladmin flush-hosts'
```

また、`FLUSH HOSTS` は長年の定番ですが、今回の8.4では構文エラーでした。古い手順書をそのまま実行すると、ここで詰まります。エラー文とマニュアルにある `mysqladmin flush-hosts` は今回試していません。

`TRUNCATE` を実行するには、**ブロックされていない経路からの接続**が必要です。今回はブロック前の接続を保持していたので実行できました。別のIPの踏み台があれば、そちらからでも実行できるはずです。どちらもなければ再起動になり、その間は全接続が切れます。

### 正常なログインが1回でもあるとブロックされない

試しに、20回ごとに正常なログインを挟んで同じ切断を300回繰り返すと、ブロックされませんでした。MySQLのマニュアルが「成功した接続なしに連続して」と書いているとおりの動きです。

ここからは推測ですが、普段からログインが成功し続けているアプリサーバーより、**たまにしか正常ログインしない接続元のほうが危ない**と考えられます。DBのポートにTCPで疎通確認だけをする監視やヘルスチェックは、今回の実験と同じ形です。また、NATゲートウェイの裏の全サーバーはDBから同じIPに見えるので、ブロックされれば全台が巻き添えになるはずです。どちらも今回は試していません。

### なぜ失敗するのか

失敗している間、シークレットの次の版（ステージ `AWSPENDING`）の値でも試すと、**そちらではログインできました**（2〜6回目で確認）。

つまり、この約60秒間はこういう状態です。

- DBのパスワードは、**もう新しい値**になっている
- `GetSecretValue` が既定で返す `AWSCURRENT` は、**まだ古い値**のまま

切り替わった先の値が取得できるようになるのは、状態が `available` に戻るころです。新旧の入れ替わりそのものは手動変更と同じく、計測間隔（約1秒）の中ではどちらも通らない時間は見えませんでした。

### 何が困るのか

**よくある「認証に失敗したらシークレットを取り直して再接続」が、1回きりだと効きません。** 取り直しても約60秒は古い値が返ってくるからです。

今回試した範囲から言える対策はこちらです。

- 再接続のリトライは**少なくとも70秒以上**続くようにする（最長で t=69.4 まで失敗したので、余裕を見て90秒程度）
- その間の認証失敗はブロックの計数に入らないので（リスク2）、この目的のリトライでブロックされる心配は小さい
- どうしても待てないなら `AWSPENDING` も試す手はありますが、**おすすめはしません。** 今回のローテーション開始直後は、版が存在しなかったり、存在してもまだログインできなかったりしました。AWSが利用者向けに保証している動きでもなさそうです

監視についても1つ注意があります。`describe-db-instances` の `SecretStatus` は、RDS経由だと `rotating` になりましたが、`RotateSecret`（Secrets Manager経由）では計測中ずっと `active` のままに見えました。ローテーション中かどうかの判定には使えません。

### 自動ローテーションでも同じなのか

RDS管理のシークレットは、既定で**7日ごと**にローテーションされます。今回の5・6回目は、Secrets Managerの `RotateSecret` で起動しました。ただし、**スケジュールで起動した本物の自動ローテーションは計測していません。** 待つと1回につき7日かかるためです。

同じ経路だとすれば、**アプリが新しい接続を張った瞬間が、毎週の約60秒に当たると失敗する**ことになります。任せる前に、接続処理のリトライが60秒を超えて続くかを確かめておくことをおすすめします。

### 切り替えのときの動き

- **管理へ切り替える：** 約2秒後に旧パスワードが失敗。シークレットの値でのログインはその直後に成功。切り替え直後の一瞬、シークレットの取得が `ResourceNotFound` になりました
- **手動へ戻す：** 約2秒後に新旧が入れ替わり。元のシークレットには `DeletedDate` が付きます。**戻したあとは古いシークレットを読みに行かないよう**、アプリ側の参照先を変えておく必要があります

どちらも既存の接続は無傷でした。

## 操作の記録に平文は残るのか

CloudTrailの `ModifyDBInstance` を確認しました。パスワードを渡した**7件すべてで、値は次のように伏せられていました。**

```text
"masterUserPassword": "HIDDEN_DUE_TO_SECURITY_REASONS"
```

拒否された変更（二重変更の2回目、使えない文字）も記録に残っていました。**誰がいつ変えようとしたかは後から追えます。**

一方で、シェルの履歴には自分の入力がそのまま残りえます。先ほどの `read -rs` はそのための一手間です（こちらは一般的な注意で、今回検証したものではありません）。

## 変更するときのチェックリスト

1. マスターユーザーをアプリから直接使っていないか確認する（AWSも非推奨としています。**分けてあれば、今回の影響はほぼ運用者だけで済みます**）
2. 新しいパスワードを先に保管先へ入れる。使えない文字が含まれていないか確認する
3. 変更前に、ブロックされていない経路で接続を1本確保しておく
4. 変更を実行し、新しいパスワードでのログインを確認する。**`available` かどうかだけで判断しない**
5. 古いパスワードを使っている接続先（アプリ、バッチ、監視、BIツール）を更新する。**既存の接続は切れないので、更新漏れは次の再接続まで見つかりません**
6. 更新後にアプリを再起動して、新しい接続が張れることを確認する

## まとめ

- 変更しても既存接続は切れない。**失敗は次の新規接続で初めて表に出る**
- 新旧の入れ替わりは約3.6秒後。約60秒の `resetting-master-credentials` はパスワードが使えない時間ではない
- 打ち間違えると、約1分は再変更できない
- 認証失敗ではブロックされない（60秒17,579回で0件）。**認証前の切断は101回目でブロックされる**
- **Host Blockedはパスワードの再設定では直らない。** `TRUNCATE TABLE performance_schema.host_cache` か再起動で解除する。8.4の `FLUSH HOSTS` は構文エラー
- ロックも権限喪失も、再設定で直った
- **Secrets Managerの即時ローテーションでは、取得した値でのログインが約60秒失敗する**（6回すべて）。リトライは70秒以上続ける

いざという時に一番効くのは、<span className="hoso">慌てて再設定する前に、エラーコードを見ること</span>です。1045なら再設定、1129なら再設定しても無駄です。この1行だけでも、手順書の先頭に書いておくと1分を節約できます。
