## はじめに

前回、Claude Code を4セッション並列で回すために、開発環境ごとの排他ロックを AI 自身に作らせた話を書きました。

あの記事の中で、こう書いていました。

> (たまにstealを何度も促されるので、ちょっとこの点はストレスかもしれない笑)

笑で流していたのですが、実際どれくらい促されているのか、数えたことがありませんでした。

envguard は acquire / deny / steal / release といったイベントを全部 `state/events.jsonl` に書き残しています。記事を書いた時点で563行だったこのファイルが、今は862行になっています。運用開始の7月9日から9月17日までの、ちょうど10週間分です。

<span className="hoso">せっかく全部残っているので、読んでみました。</span>この記事はその結果です。

## 先に結論

- **ロックの譲り渡しは、人間の steal より機械の自動解放のほうがずっと多かった。** 人間が奪ったのは40回、30分アイドルによる自動解放は76回。
- **拒否273件のうち、4分の1近くが誤検知だった。** `grep` のパターンに含まれる `=>` や `->` を出力リダイレクトと読んでいた。`git -C` でサブコマンドを見失っていた。
- **「steal を促される」ストレスの正体は、この誤検知だった。** 読み取り専用の grep が拒否され、AI が言い回しを変えて再試行し、また拒否される。3分間に8回拒否された日もある。
- **コードは7月9日から一行も変えていない。** ログを読むまで、直す場所が分からなかった。

## 数字で見る2か月

集計は、ログを Node のスクリプトで読んで数えただけです。イベントの種類ごとの件数はこうなっていました。

```
acquire   295   ロック取得
deny      273   ブロック
release   175   解放（セッション終了・/clear など）
takeover   79   自動引き継ぎ（idle-expire 76 / stale 3）
steal      40   人間による奪取
```

セッションは全部で214本。そのうち書き込みまで進んでロックを取ったのが188本、少なくとも1回ブロックされたのが95本です。

<span className="hoso">半分近いセッションが、どこかで一度はブロックされている</span>ことになります。4面あるとはいえ、実際の作業は env1 に集中していました。イベント862件のうち578件が env1 です。開発の本流がそこにあるので当然なのですが、「4面あるから足りるだろう」という前回の見立ては甘かったです。

ブロックされた95本のセッションがその後どうなったかも追ってみました。

- **58本は、その環境を二度と取れないまま終わった。** 別の作業に切り替えたか、読み取りだけで済ませたか、あきらめたか。
- **24本は、steal なしで後から取れた。** 保持者が30分書き込みをせず、自動解放されたケースです。
- **13本だけが、人間の steal を経て取れた。**

前回の記事では「ブロックされたら人間が明示的に奪う」を設計の柱として書きました。でも実態は、<span className="hoso">人間が奪う前に30分の自動解放が先に効いている</span>ケースのほうが多かった。steal 40回のうち、直前の拒否から5分以内に打たれたものは12回しかありません。残りは、拒否からずいぶん経ってから「ついでに空けておくか」で打ったものです。

30分という数字は「一度書いたきりのセッションが後続を飢えさせないため」の保険のつもりで入れたのですが、これが主役でした。

## 拒否の中身を読む

ここからが本題です。273件の deny のうち、Bash が260件、Edit が10件、Write が3件。Edit と Write は file_path で環境を判定しているので、ほぼ誤検知はありません。問題は Bash です。

deny イベントにはコマンドの先頭120文字が残っています。それを、envguard 自身の判定ロジックにもう一度通して「なぜ書き込み扱いになったか」を分類しました。

```
redirect（引用符の中の => や ->）   32
git -C                             25
docker exec                        12
python3 / php / node の起動          12
出力リダイレクト（本物）              20
rm / cp / mkdir / sed -i など（本物） 15
複数行スクリプトで判定不能           86
```

上の3つ、合わせて69件は明らかに読み取り専用のコマンドです。238件中の29%。<span className="hoso">「複数行で判定不能」の86件にも同種のものが混ざっている</span>ので、実際の誤検知率はもう少し高いはずです。

### 誤検知1：`=>` を出力リダイレクトと読んでいた

envguard は Bash コマンドを見るとき、まず `2>&1` と `>/dev/null` を無害として取り除き、それでも `>` が残っていれば「ファイルへの書き込み」とみなします。

<CodeBlockTitle title="envguard.mjs（抜粋）" />

```js
const stripped = cmd.replace(/\d?>\s*&\d/g, '').replace(/\d?>{1,2}\s*\/dev\/null/g, '');
if (/>/.test(stripped)) return false; // 読み取り専用ではない
```

この判定は、引用符の中身を見ていません。だから Laravel のコードを探すこういう grep が全部引っかかります。

```bash
grep -rn "->email = \|'email' =>" app/ | head -40
grep -rn "request()->ip()\|\$request->ip()" app/
grep -n "getRelatedDataTypes\|const \|DATA_TYPE\|=>" app/Models/...
```

PHP の配列は `=>`、メソッド呼び出しは `->`。<span className="hoso">Laravel のコードベースで grep を打てば、まず間違いなくどちらかが入ります。</span>envguard を使っている環境は全部 Laravel なので、これは設計時点で気づくべきでした。

### 誤検知2：`git -C` でサブコマンドを見失っていた

git は `log` / `status` / `diff` / `fetch` など読み取り専用のサブコマンドを許可リストで持っていて、それ以外を書き込み扱いにしています。判定は「`git` の次の単語」を見ます。

```js
if (w0 === 'git') {
  const sub = words[1];
  if (RO_GIT.has(sub)) return false;
  return true; // 未知/書き込み系の git サブコマンドは書き込み扱い
}
```

`git -C /path/to/repo log` と書くと、`words[1]` は `-C` です。許可リストには無いので書き込み扱い。

Claude Code は cwd を動かさずに別のリポジトリを見るとき、`git -C` を多用します。25件、全部これでした。

### 誤検知3：`docker exec` は中身を見ない

`docker exec postgres psql -U postgres -l` のような、データベース一覧を出すだけのコマンドも12件拒否されていました。docker の判定は `ps` / `logs` / `inspect` などの許可リストで、`exec` は一律に書き込み扱いです。

これは誤検知と言い切れません。`docker exec` の先で何が実行されるかは、その先を読まないと分からないからです。ただ、拒否された12件の中身を見る限り、少なくとも一覧表示の類は混ざっていました。

## 「steal を促される」ストレスの正体

拒否されたとき、AI にはこういうメッセージが返ります。

```
[envguard] env1 は別の Claude Code セッションが使用中のため Bash をブロックしました。
保持者: session b46bcf5e (cwd: ~/dev/hrd_laravel_projects/sc_dev_laravel, 取得 10:12, 最終活動 3分前)。
読み取り専用の作業は可能です。ユーザーが奪取を明示的に指示した場合のみ `envguard steal env1` を実行してください。
```

「読み取り専用の作業は可能です」と書いてあります。AI はこれを素直に受け取ります。<span className="hoso">自分が打ったのは grep だ、読み取り専用のはずだ、なら書き方を変えれば通るはずだ、と考えて再試行する。</span>そしてまた `->` が入っているので拒否される。

9月15日のログがまさにそれでした。

```
15:54  grep -Hn -i "i..."  .env* の中の IP 設定を探す                     deny
15:56  grep -rn -E "allowed_ips|REMOTE_ADDR|X-Forwarded|->ip\(\)|..."   deny
15:56  （同じ grep を 2 回打ち直し）                                      deny ×2
15:56  grep -rn "request()->ip()\|\$request->ip()\|Request::ip()" ...  deny
15:56  grep -rn -- "->ip\b" ...                                          deny
15:57  grep -n "=> \[\|'company_name'\|'service_name'\|hosts_allow..."  deny
```

同じセッションが3分の間に8回拒否されています。IP アドレスの扱いを調べたいだけなのに、`->ip` や `=>` を含む限り何度書き直しても通らない。結局このセッションは steal されることもなく、保持者側が 16:22 に `/clear` で env1 を手放すまで、そこに書き込めないままでした。

つまり、<span className="hoso">「steal を何度も促される」のは AI が横着だからではなく、読み取り専用のコマンドを拒否しておきながら「読み取りは可能」と伝えている、こちらの矛盾のせい</span>でした。8月31日に6回、9月10日に6回、8月25日に5回が2度。同じ形のバーストが、記事を書いた後だけで6回起きています。

前回「ちょっとストレスかもしれない笑」と書いたものは、笑いごとではなく実装バグでした。

## 直すなら、この2箇所

判定ロジックは `isReadOnlyBash` と `segmentMutates` の2つの関数に閉じています。直すべき箇所も2つです。

**1. リダイレクト判定の前に、引用符の中身を潰す。**

```js
// シングル/ダブルクォートの中身を空にしてから > を探す
const unquoted = stripped.replace(/'[^']*'/g, "''").replace(/"[^"]*"/g, '""');
if (/>/.test(unquoted)) return false;
```

これだけで32件が通ります。`echo "a -> b" > out.txt` のような本物のリダイレクトは、引用符の外に `>` が残るので引き続き捕まります。

**2. `git` のサブコマンドを探すとき、`-C <path>` と `-c key=val` を読み飛ばす。**

```js
let i = 1;
while (words[i] === '-C' || words[i] === '-c') i += 2;
const sub = words[i];
```

こちらで25件。

`docker exec` は据え置きにします。先で何が動くか分からないものを通すと、拒否リスト方式の意味がなくなるからです。psql の一覧が見たければ、ホスト側から `psql -l` を打つか、読み取り専用の面で試すかで済みます。

なお、この2つはまだ手元に当てていません。ログを読んで分かったことをこの記事に書き、記事を書き終えたら当てる、という順番にしています。<span className="hoso">直してから書くと「直す前に何が起きていたか」の数字が取れなくなる</span>ので、今回は先に数えました。

## 「もうすぐ要らなくなる」はどうなったか

前回の余談で、Claude Code on the web のようなクラウドサンドボックスが普及すれば、この手のローカル多面環境はそのうち要らなくなる、と書きました。

実際に Claude Code web を使ってみた記録は別の記事にしています。

結論だけ書くと、<span className="hoso">「丸ごと置き換え」にはなっていません。</span>サンドボックスから外に出られるのは 443 番だけで、手元の Docker で動いている PostgreSQL や、VPN の向こうにある社内システムには届きません。レガシーな環境ほどクラウドに乗らない、という前回の懸念はそのままでした。

envguard のログを見ても、9月に入ってからの17日間で155件のイベントが出ています。1日あたりのペースは7月より落ちていますが、要らなくなる気配はありません。作ったのが6月、「要らなくなるな」と思ったのが8月、それでも9月も使い続けているのは、少し皮肉です。

## よくある質問（FAQ）

### Q. 誤検知が3割もあるなら、許可リスト方式にしたほうがよかったのでは？

いいえ。許可リストにすると、未知の CLI を使うたびに引っかかります。今回の誤検知は「引用符の中を見ていない」「オプションを読み飛ばしていない」という判定の粗さであって、方式の問題ではありません。拒否リストのまま判定を丁寧にするほうが安く済みます。

### Q. 30分のアイドル自動解放が主役なら、steal は要らないのでは？

要ります。30分待てないケースが実際にあり、それが steal 40回のうちの12回です。ただ、前回書いたほど「人間の判断が柱」ではなかったのは確かで、自動解放の時間を20分に縮めるほうが、steal の回数を減らす効果は大きいと思います。

### Q. ログを残しておいて何の役に立ちましたか？

これがなければ、この記事の数字はひとつも出せませんでした。「ストレスかもしれない」という感想が「3分で8回拒否されている」という事実になり、「拒否リストの判定が粗い」という原因まで辿れました。AI に作らせたツールほど、動いているように見えて何をしているか分からないので、イベントログは最初から必ず付けたほうがいいです。

### Q. Claude Code の hooks 以外でも使えますか？

hooks の stdin に流れてくる JSON を読んでいるだけなので、同じ形式で `session_id` / `cwd` / `tool_name` / `tool_input` を渡せるものなら動きます。ただ、ロックの生存判定に Claude 本体のプロセス ID を使っているので、そこは差し替えが要ります。

## まとめ

- envguard の2か月分のイベントログ862行を集計した。セッション214本のうち95本がどこかで1回はブロックされていた
- **ロックの譲り渡しは、人間の steal（40回）より30分アイドルの自動解放（76回）のほうが多かった。** 設計の柱だと思っていた「人間が奪う」は脇役だった
- **拒否273件のうち、少なくとも69件は読み取り専用コマンドの誤検知。** `grep` パターンの `=>` や `->` をリダイレクトと誤読、`git -C` でサブコマンドを見失う、の2種類でほぼ説明がつく
- **「steal を何度も促される」ストレスは、この誤検知が原因だった。** 読み取り専用の grep を拒否しながら「読み取りは可能」と伝える矛盾に、AI が律儀に付き合っていた
- 直す箇所は2つ。引用符の中身を潰してから `>` を探す、`git -C <path>` を読み飛ばしてサブコマンドを見る
- 「もうすぐ要らなくなる」は外れた。9月も使い続けている

感想だけで済ませていたことを数字にすると、原因まで辿れました。AI に作らせたツールは、最初にイベントログを付けておくのが一番の投資だと思います。
